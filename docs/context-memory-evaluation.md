## 1. 目标与范围

验证 CLAWKIT 的上下文压缩、工作记忆、工作区进度、历史会话召回和长期记忆是否帮助 Agent 正确续接任务，并量化这些机制的净消耗。首期由自动化评测提供证据，不以用户连续使用多天为前置。

核心问题：

1. 旧消息离开近期窗口后，Agent 是否仍遵守用户目标、操作范围和已确认决策？
2. 切换会话或重建进程后，能否接着未完成步骤工作，避免重复已完成操作？
3. 记忆是否找回了必要证据，是否误用旧事实、跨项目信息或未确认猜测？
4. 在相同完成标准下，是否减少总 Token、重复查证和重复询问？
5. 哪些失败需要结构化任务检查点，哪些通过现有摘要、检索和工具说明即可修复？

首期不把生产 MTTR、人工节省分钟数、商业用户规模作为验收要求；这些字段没有数据时明确记为未测量。不预设记忆一定有效，不以添加向量库、知识图谱或新的 Agent 框架作为完成条件。

## 2. 当前事实与缺口

| 部分 | 源码事实 | 需要补的证据或机制 |
| --- | --- | --- |
| 会话压缩 | `DefaultContextPipeline` 在模型调用前分级处理；深度压缩独立插入并校验约束快照 | 多次压缩后的语义连续性、实际模型任务结果、净 Token 与缓存影响 |
| 正则约束 | `ConstraintExtractor` 匹配路径、错误码、`[ ]` 待办，扫描消息内容 | 不识别一般自然语言决策或已完成步骤；不能据此宣称完整里程碑管理 |
| 结构化锚点 | 运维诊断的 `OpsCompactionHintProvider` 从事件与证据状态生成锚点；普通 Engine 默认 GENERAL | 一般任务的目标、决策、完成条件如何进入并持续更新保护区 |
| Working Memory | `remember` 工具保存进程内键值，每轮回注，清空会话时清除 | 是否避免重复查证；被清除后的任务恢复不能归功于这份进程内状态 |
| Workspace State | `.clawkit/todo.md`、`plan.md` 保存计划和进度 | 已完成、待确认、待执行状态能否正确续接；重建进程与仅清空会话分别测量 |
| 长期记忆 | 普通 CLI 装配 `DefaultMemoryHooks`；提取对话中的可复用内容，存 Markdown 并按名称/描述 BM25 召回 | 提取是否忠实、改写提问能否召回、冲突/旧事实是否误导；当前 `MemoryEntry` 没有来源 ID 和 revision，同文件名更新会保存新内容 |
| 历史 Session | 保存时生成摘要；BM25 搜索名称、首条用户消息与摘要；自动注入最多三条摘要 | 摘要是否漏掉答案，自动召回是否引入弱相关信息；`session_context` 返回摘要，详细消息通过 Session 加载 |
| 现有 Runtime 评测 | `BenchmarkRunner` 构造 `ScriptedProvider`，16 个固定回归用例 | 可以复用夹具、评分、事件和报告，不能把原分数当作真实模型记忆效果 |

## 4. 功能需求

| ID | 需求 | 验收方式 |
| --- | --- | --- |
| CM-R1 | 区分会话历史、进程内工作记忆、磁盘进度、历史会话摘要、长期记忆与审计事件 | 各自记录来源、持久化范围、注入次数和 Token；清空会话/重建进程分别验证 |
| CM-R2 | 检查压缩后的目标、约束、决策、事实和未完成步骤 | 同时检查快照完整与后续行为；“文本在”不等于“Agent 遵守” |
| CM-R3 | 必要时增加有界任务检查点 | 只保护来自用户或已验证程序结果的状态；模型假设保持未确认；不靠正则猜测语义完成 |
| CM-R4 | 检查提取、检索、使用的独立错误 | 记忆有无必要事实、召回是否覆盖全部来源、模型是否正确应用分别评分 |
| CM-R5 | 历史信息不能伪装成当前运维事实 | 旧结论可指导下一步采证；当前恢复/写操作资格仍由新鲜独立证据决定 |
| CM-R6 | 工作区、目标与实验实例隔离 | 每个实例有独立临时 HOME、工作区、Session/Memory/Run 目录；跨项目信息不可混入 |
| CM-R7 | 评测结果与用量可复核 | 同时保存完整失败、评分版本、原始运行轨迹、实际 usage 及缺失 usage 标记 |
| CM-R8 | 不牺牲任务质量换取压缩率 | 首先报告完成情况与违规，再报告消耗；不得只对成功样本统计低 Token 后宣传全局效率 |

### 4.1 任务检查点的候选设计

此部分是待评测验证的方案，不代表已实现。

优先从现有计划/进度更新、用户确认和工具结果生成检查点，候选字段为：taskId、revision、阶段目标、用户约束、已确认决策、完成条件、验证通过的产物、待执行/待确认步骤、来源 message/run/evidence 引用与时间。初期不增加每轮模型总结，不默认增加新工具；需要改变公共契约时先形成具体接口再审阅。

检查点写入工作区，更新只替换同一任务的当前状态；旧 revision 保留可追溯来源。经过验证的完成步骤进入已完成集合，待确认步骤不能自动变成完成。基于现有 `CompactionAnchor` 映射必要状态，检查数量和 Token 预算；摘要只是索引或压缩表示，不能成为新的事实来源。

正则只承担 ID、路径、错误码等格式识别。一般自然语言约束的识别完整性、重复压缩后检查点是否延续、长约束无法容纳时是否明确失败，均由用例验证。

### 4.2 正则候选的来源边界

正则识别到的路径、错误码与 TODO 只表示消息中出现了对应文本。用户消息中的既有关键约束继续作为 required USER_CONSTRAINT 保护；系统派生片段、普通工具输出和模型叙述不得因此变成已确认的用户约束。工具文本仅保留为可选 OPEN EVIDENCE，模型文本为可选 OPEN_HYPOTHESIS；系统片段由原有系统消息保护与显式 workflow anchor 表达必要状态。

同一文本的候选按来源可信度合并，用户来源不被低可信来源覆盖；调用方显式锚点及其 required、state、evidenceRef 合同不变。必要锚点超预算仍明确失败，不通过提高预算或静默删除必要约束修复。retainedConstraints 只报告最终上下文仍含有的原始匹配文本。验收覆盖原始工具路径溢出、角色区分、来源合并、真实用户约束溢出和显式工具证据锚点；这一机制回归不证明开放任务完成率提高。

### 4.3 验证策略与任务收尾

`ActionDescriptor.verificationMode` 由工具或可信组合根声明，模型不得改写。`DETERMINISTIC` 以现场重新读取目标并检查全部声明断言为准，不启动额外模型解释；断言缺失、未知或不匹配仍失败。`WORKFLOW` 保留现有独立根、只读权限与确定性断言先行的复查链，模型解释不能推翻断言。`MANUAL_REQUIRED` 不自动验证成功。

模型写出了正确文件、文件动作得到验证、整个任务完成分别评分；确定性文件动作不能因此替代现场业务恢复验证。所有实际发生的验证模型调用继续共享评测额度，不在新根重新领取预算。机制验收须包含写入后目标漂移、人工策略匹配文件仍不自动成功、普通文件任务的有界收尾以及工作流跨根用量。

### 4.4 文件查找与现场证据

递归文件模式中的独立 `**/` 匹配零层或多层目录，`**/*.json` 包含工作区根目录文件；Glob 和 Grep 的可选 glob 过滤共用匹配规则。普通 `*` 不跨目录，NIO 原有字符组、转义和备选模式保留；非法或展开超过 256 个变体的模式返回 `T-002`，不将异常伪装为无匹配。工作区、输出上限和写前权限不变。

这是工具合同与模型预期对齐：Java [NIO glob](https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/nio/file/FileSystem.html#getPathMatcher(java.lang.String)) 将目录分隔符按字面匹配；[ripgrep globset](https://github.com/BurntSushi/ripgrep/blob/master/crates/globset/src/lib.rs) 的递归目录通配支持零层目录。本项目保留 NIO 匹配器，仅补有界的零层目录变体，不引入搜索库。

续接回归必须在实际 Engine 中查找到根目录现场文件、读取后生成产物，并保持已验收文件不变；单纯看到摘要或哈希正确不能代替这些条件。固定响应只能证明该工具与评测链，修复后的模型行为需另轮验证。

## 5. 两套独立对照

### A：会话压缩与任务续接

关闭跨会话召回以隔离压缩效果，统一任务、模型、原始信息、工具、输出预留与上下文预算。

- C0：按近期完整 Turn 窗口截断；不得破坏 tool call/result 对。
- C1：滚动摘要＋近期窗口，作为常见压缩强基线；摘要模型与可用预算固定。
- C2：当前分级压缩与锚点保护。
- C3：仅在开发集证据支持后加入任务检查点的候选版本；必须重新冻结版本和比较配置。

完整历史装得下时另设只用于诊断的 full-context 上界；装不下时记为不适用，不能偷偷提高模型窗口。正式主对照必须包含强基线和原版本；候选组的选择在看到正式结果前固定。

### B：跨会话记忆与知识复用

各组使用相同会话压缩和任务工具，区分可访问的历史存储策略。

- M0：无跨会话记忆，作为收益下界；不允许从共享目录读取上次记录。
- M1：完整历史文件档案＋有界 Read/Grep，作为简单但有力的基线。搜索/read 工具受工作区和输出预算限制。
- M2：当前长期记忆与历史 Session 摘要 BM25 召回。
- M3：只有开发集发现误召回、漏召回或更新问题时，加入有针对性的门控/来源/版本候选；不预先要求向量检索。

首次会话的原始信息一致。M1 的可访问档案与 M2 的提取过程分别记录，不能给某组额外人工编写的答案记忆。自动摘要、记忆提取和显式 `remember` 的使用单独标注。

固定 Workspace State 与 Working Memory 设置；另做组件消融观察它们的贡献，不能一次关闭所有机制后将全部差异归功于长期记忆。需要验证磁盘进度本身的恢复时单独登记场景。

### 5.1 案例家族

| 家族 | 要观察的行为 |
| --- | --- |
| 目标与范围 | 多轮工具输出后仍只修改指定文件或处理指定目标 |
| 阶段续接 | 已验证阶段不重复执行，待确认步骤不被跳过 |
| 决策与事实 | 保留先前决定所依赖的事实，能回到来源核对 |
| 纠正与冲突 | 明确采用最新确认信息；保留旧事实的历史含义，不将假设升级为事实 |
| 跨会话表达变化 | 同义改写、不同关键词、多来源组合仍能找回必要信息 |
| 无答案与弱相关 | 未知时说明缺证；相似项目、错误目标、弱关键词重合不诱发错误行动 |
| 环境变化 | 历史服务结论已失效时重新采证，不能用记忆自证恢复 |
| 来源与预算 | 工具输出中的指令式文字、坏摘要、超多锚点和缺失证据不能静默改变任务状态 |

开发案例与正式留出任务分离。正式任务的名称、路径、状态组合和叙述与开发案例不同；不能只改随机种子后宣称跨任务泛化。共享背景下的多道问题属于一个统计块。

## 6. 评分口径

| 指标 | 定义与分母 |
| --- | --- |
| 任务完成 | 独立检查文件/结构化产物/服务行为满足全部预注册条件。分母是所有已尝试任务；预算、协议、网络失败分别保留，不用系统兜底替代模型完成 |
| 约束遵循 | 满足的行为约束数/必须检查的约束数；另报每个任务是否有任一严重违规 |
| 检查点连续性 | 已完成步骤被重复执行、待办被遗漏、待确认被跳过的任务数；由真实工具轨迹和产物检查 |
| 提取忠实度 | 提取记忆中的正确、缺失、矛盾和无来源事实；不能仅按 JSON schema 成功评分 |
| 来源召回 | 明确 session/message/evidence 粒度；分别报告全部必要来源命中与任一来源命中，不混叫 Recall@k |
| 召回精确率 | 相关来源数/实际召回来源数；多次召回去重。无答案题单列误召回与合理未知，不套有答案 Recall 分母 |
| 重复查证 | 同目标、相同查询范围且证据未变的冗余读取/请求；必须的新鲜 Precheck 和独立验证不记为冗余 |
| 净消耗 | 全部阶段的实际 input/output/total/cache hit/cache miss；包含摘要、记忆提取、保存 Session 摘要、主任务、子任务、纠错和重试 |
| 时延 | 检索和模型处理分开；端到端耗时包含预定义验证等待。重放输入不计算为真实采证耗时，人工审批等待不当作 Agent 处理时间 |
| 重复一致性 | 同一任务重复执行的通过情况及全部重复均成功的任务占比；按任务块统计置信区间，不把多轮回答或重复执行扩大为独立任务数 |

净 Token 改善同时报告全部尝试的总消耗、完成数和失败率；对两组都成功的配对任务可单列消耗变化，但需公开这个子集的覆盖率。摄入成本另报一次构建成本、每次查询成本和指定查询次数的总账，不任意假设无限查询摊薄成本。

来源评分预先固定：SourceRecall@k 是召回必要来源的比例；AllEvidenceHit@k 是是否覆盖全部必要来源；AnyEvidenceHit@k 是是否命中至少一个来源。等价证据可登记为多个可接受来源集合，满足一个完整集合即可；不能把重复副本当作更多必要来源。无答案题不进入这三项的有答案分母。

差异与 95% 区间采用预注册的配对任务块 bootstrap，记录重采样种子；同任务的所有重复执行一并进入一个块。模板派生任务另外报告按家族聚类的敏感性分析。小样本同时公开逐任务计数，不把宽区间写成稳定收益。

cache hit/miss 是 input 的子项，reasoning 按 Provider 合同属于 completion 的子项时不重复相加；调用 Token 汇总不能再叠加工具输出的本地估算。本地估算只用于预算和分区解释，actual usage 才进入实际用量账本。

费用只有在实际用量与固定价格/cache 口径可取得时估算，并与实际扣费区分；缺失 usage 不记零。不以压缩前后的一次 Token 差代替整个任务的净收益。

本地任务以程序检查为主；开放问答可用固定 judge 和 rubric，抽查错误/正确边界，保存分歧与原始输出。采用官方 LongMemEval judge 或改动评分器时明确区分版本与口径，不把宽松字符串匹配包装成普遍语义准确率。

## 7. 运维评测的取舍

[Google SRE 的 Incident Metrics 报告](https://sre.google/resources/practices-and-processes/incident-metrics-in-sre/)讨论了故障持续时间高方差与样本不足对 MTTR/MTTM 趋势判断的影响。对 CLAWKIT 的推论是：目前受控故障和固定验证窗口适合检查处置合同，不能直接推断生产恢复效率。

近期保留以下可自动评分的结果：

1. **处置选择正确率**：事前标记 INVESTIGATE/WAIT/ASK/授权修复/交接，按任务分别评分；无效模型提交和系统兜底不计模型正确。
2. **合资格任务的独立恢复**：分母事前固定；结果未知即使外部已恢复，仍按产品终态报告，不能事后移出分母。
3. **禁止、重复及假恢复**：报告实际动作数和故障条件；控制器对象重建与实际进程重启、传输断连分别标注。
4. **人工交接质量**：目标、当前证据、未确认点与下一步是否正确且齐全。必要交接与可避免的额外询问分开，不奖励盲目降低人工介入。
5. **采证与调用消耗**：步骤、实际 Token、证据读取和冗余请求；业务端独立检查不被优化掉。

实验墙钟耗时只作为同场景、同注入、同模型、同验证窗口的附加数据，名称为“受控任务完成耗时”。不称生产 MTTR，不据此宣称节省人工工时；真实效率后续取得基线时再补。

## 8. 执行与证据合同

复用 `clawkit-evaluation` 的夹具、Scorer/Reporter 和现有 FileRunRecorder/RunReader；新增独立 Suite 与真实 Provider 适配，不改写 `runtime-v1` 的脚本回归含义。基于现有 Runtime 依赖装配注入独立 MemoryHooks、SessionStore、ContextPolicy。

运行类型必须分开：

- `mechanism-replay`：无网络、固定模型响应，证明存储、边界、计量和保护不变量。
- `live-continuation`：重放事前冻结的长历史，由真实模型完成压缩/提取与后续任务；证明长历史续接效果，不称全程真实多轮任务。
- `live-full`：历史在完整真实任务过程中形成，所有模型/工具调用计入；用于满足现有真实 20+ Turn 长任务门禁，重放不能替代。

生产隐私目录与凭据不能成为评测输入。首次使用自建合成任务及获准的公开数据；每实例使用临时目录和固定测试工具。显式真实模型评测才保存原始交换，普通用户日志策略不变。

每轮至少保存：

- manifest：源码/数据/任务/评分器/提示/工具/模型/配置哈希、所见模型别名、时间、预算、缓存规则、组别和执行顺序；
- 原始历史、来源 ID、模型和工具轨迹、压缩前后分区数据、召回来源与记忆版本 sidecar、最终产物；
- `instances.jsonl`、逐任务评分、usage ledger、失败分类、summary 和独立复算回执。

答案、来源标签、预期动作和验收脚本只由 evaluator 读取，Agent/记忆模块看不到题型或真值。失真摘要与工具输出不允许修改评分器或标准答案。

所有失败保留；网络、预算、不可评分、未运行分开记账。失败后再次运行产生新轮次，不覆盖旧实例。采用组间平衡/交错顺序；每次重复重置状态，除非任务本身要求会话之间共享记忆。

普通 CI 只执行离线合同，不调用真实模型。真实运行为显式入口，每轮有总请求/Token/时限上限并先预留单任务额度；历史一次性 DeepSeek 诊断授权不自动适用于新评测，执行前确认具体预算与数据范围。

### 8.1 离线入口与独立复核

离线入口为 `clawkit-evaluation` 的 `context-memory-replay` Maven profile。固定响应复用真实 `DefaultContextPipeline`、`SessionService`、`DefaultMemoryHooks` 和磁盘存储；引擎接入测试另覆盖会话加载、进度注入、只读采证、写工具与独立验证。显式 Hint 案例只验证已有 Anchor 合同，不意味着通用引擎已经自动生成自然语言检查点。

```powershell
mvn -B -ntp -pl clawkit-evaluation -am -Pcontext-memory-replay verify '-Dcontext.memory.output=tmp/cm-replay-new-run'
mvn -B -ntp -pl clawkit-evaluation -am -Pcontext-memory-replay verify '-Dcontext.memory.mode=audit' '-Dcontext.memory.output=tmp/cm-replay-new-run'
```

每次执行必须使用全新输出目录；目录已存在时拒绝覆盖。目录内的 `frozen-cases.json` 保存评测脚本和真值，`agents/<id>/` 只保存该实例的 HOME 与工作区；`instances/<id>/agent-input.json`、模型请求和记忆提取输入不包含真值或评分器。`manifest.json` 冻结数据与公开源码哈希；`artifact-hashes.json` 检测缺失、增加或修改的产物。独立 audit 从原始 observation、gold 和 usage 重算，不采信 `instances.jsonl` 或 `summary.json` 中的得分。

来源 sidecar 区分原始 Session、压缩派生与记忆派生，记录输入来源、内容哈希、revision 与原观察时间。派生关系仅表示“处理过这段历史”，不能据此认定每条模型结论都有可靠依据。上下文记录保留来源和生命周期；Working Memory、历史 Session 摘要、长期 Memory 使用各自固定注入标记细分。上下文 Token 数是估算，实际消耗只读取 Provider usage；缓存输入和 reasoning 输出作为子项单列，不再次加入 total。模型收到但解析失败的响应也计入用量与失败。

评测共享预算在网关收口，跨摄入、压缩、Session 摘要、主任务和独立验证 root 累计；保留原调用的取消、deadline 和预算限制。Token 账本沿用 Provider 预留与实际结算语义，实际消耗超过估算时停止后续调用并保留超额事实；真实轮次还须冻结输出上限与请求预留规则，不能只依靠事后结算声称严格消费上限。

首批风险分类中，多来源召回报告 Source Recall、All/Any Evidence Hit 和 Precision；未知查询单独标记，不混入可回答查询 Recall。正则、锚点文本或固定产物的断言用于机制回归，不能作为开放任务语义准确率。

开发任务定义在 `benchmarks/context-memory-dev-v1.json`：六个独立任务按压缩与跨会话分别分配三种对照，共十八实例。题型、预期答案、必要证据来源集合和评分规则只由 evaluator 读取；Agent 只接收当前组有权使用的原始历史与工作区。历史自身的身份、revision、时间属于来源信息，可以随原始档案呈现，不含“此来源是正确答案”等标签。该文件是开发集，不能与后续冻结留出集混为正式分母。开发轮次的预算、模型和输出上限按 manifest 冻结；准备数据与已运行结果分别记录，当前验收状态见 TODO。

### 8.2 开发对照执行器合同

`ContextMemoryContinuation` 的默认模式为 `prepare`：不读 API 凭据，不创建网络 Provider。它使用生产引擎加载保存的历史，在第一次上下文构建与压缩边界停止；检查实际分词、原始上下文压力、保护提示与最近三轮能否装入预算。压力未超过 compact 线、退成字符估算或最近轮次装不下时，保存失败并拒绝真实调用。当前 Engine 将原始上下文交给选定 Pipeline；遮蔽与分层压缩属于该 Pipeline，C1 基线采用自己的摘要策略。各组共用 Engine、Provider、工具和预算，对照变化发生在 Pipeline 或历史检索阶段。历史运行 manifest 中 “common Engine always-on masking” 的描述有误，原始用量与评分不因此重写。

```powershell
mvn -B -ntp -Pcontext-memory-continuation clean verify '-Dcontext.memory.continuation.output=D:/Agent/miniclaw/tmp/cm-development-prepare-new-run'
```

执行器及合同测试已完成离线运行；全仓库干净验证、压力准备与真实运行分别验收，当前状态见 TODO。独立复算测试覆盖已保存的工具事件、实际用量格式和最终文件被修改后的重新判分，固定响应仍只证明机制。压缩任务使用显式的 4096 Token 评测窗口，不能将它说成供应商的原生容量。当前候选配置为最近三轮、temperature=0、每次最多 1024 输出 Token、关闭 reasoning、阻塞请求、零传输重试；正式对照前按准备结果校验并冻结，不能按已观察到的模型得分调参。

六组使用相同四项任务工具：`read/write/glob/grep`。评测端同步过滤模型工具列表和上下文工具预算，禁止调用未提供的内部任务或记忆工具；独立验证仍受原只读工具集合约束。M0 无历史；M1 可通过相同工具读取全部原始历史档案；M2 使用原生记忆抽取、Session 摘要和 BM25，保存摄入结果与每版磁盘内容后重开存储。M2 的原生时间戳是摄入时间，原观察时间单独留档，不假定摘要已经保留时间与事实来源。

调用顺序按任务配对，每套三个任务轮换先执行的组，固定随机种子。每实例共享总额度覆盖全部阶段，整轮另共享 Token 池和请求许可；独立验证新 root 不会获得新额度。工具按模型提出的调用保守计数，所有 root 共用十六个许可，超限整批拒绝、已预留许可不退回，实际工具执行不会超过该上限。发送前检查 UTF-8 输入字节、framing 余量和输出上限组成的保守预留假设；它不是供应商收费承诺。收到但缺失实际 usage、消耗超过该假设或评测器无法归档时，保留原始交换与用量，停止整轮，其余实例逐项记为未运行。

`frozen-data.json`、`ordered-instances.json` 和 manifest 固定分母、参数与顺序；`source-inputs/` 保存源码、测试与构建文件精确字节，运行结束检查源码未变。独立 audit 从原始响应、已保存工具事件和最终工作区重新计算用量、主任务状态与输出结果。禁止写入已完成文件、写入额外文件、遗漏现场读取或停止在预算/协议失败，都不能以模型自述“完成”覆盖。

评分错误列表按完整多重集合做规范排序，避免 Map 迭代顺序跨 Java 进程变化造成误报；错误内容、重复数、结果字段与状态均须一致，时间顺序以原始事件为准。审计器修复需另存版本、源码哈希与新回执，不重写原始轮次。

Java audit 计算可机械验证的结果与用量；评测额外保存全阶段事件，覆盖没有完整 Run 生命周期的摄入、Session 摘要与压缩调用，并与实际任务 Run 事件交叉核对。

`scripts/review-context-memory-continuation.mjs` 从封存产物生成独立审核包：原始来源、每条预期事实的来源集合、磁盘提取结果与摘要、主任务实际收到的模型输入分开呈现。独立验证的输入不计作主任务召回。审核包与标注保存在封存目录之外，不能写入 Agent 的工作区。标注需记录审核者与方法，覆盖全部已运行记忆实例和每条事实，并引用存在的原文与派生材料；错误来源、模型猜测、错阶段、漏标或哈希变化都会拒绝复算。

原文引用和哈希只证明出处，语义支持由审核者判断，不能自动据此推断蕴含关系。审核结果区分提取保留与实际输入保留，未知查询不混入可回答事实分母；未识别完整召回排名时，Recall@K 与 Precision@K 保持不可评分。每轮真实事实支持与召回效果须在实际产物上完成审核，记录是否盲化以及审核者身份；固定响应审核合同不构成效果数据。默认准备与机制回放都不关闭真实 20+ Turn 门禁。

真实模式要求 `CLAWKIT_CONTEXT_MEMORY_EVALUATION=true`、显式 `live` 模式及独立的人类数据范围/预算授权；环境开关本身不构成授权。输入仅限这份合成开发集和隔离工作区，不加载私人项目配置或服务器数据。CI 只运行离线合同，历史诊断授权不复用。

### 8.3 正式冻结入口

正式留出集及分阶段合同见 [冻结验证实施方案](context-memory-frozen-validation-plan.md)。`ContextMemoryFrozen` 是单独入口，默认无网络准备，严格检查24个任务、每套12个、3次重复和216实例；压缩为摘要强基线/冻结原版Context/候选Context，记忆为无历史/原始档案/原生Memory+Session。正式输出上限仍为1024，任务工具上限为24次提议，整轮最多2小时；新预算不能复用开发授权。

原版Context只加载已封存实现，其他运行时共享；记录编译结果、JAR哈希及真实加载来源。新增多产物评分、当前文件观测来源、任务块统计和独立用量复算。历史事实与当前文件事实分开审核，后者不纳入记忆提取保留率。固定摘要压力探针、离线合成账本和预检只证明机制，不能代替正式216运行或独立真实20+Turn。

| CM-E3 针对失败修复 | 按开发集结果选择任务检查点、历史 Digest、召回门控、来源/冲突处理中的必要项；复用 P2 既有设计 | 不预设每项都开发；修复有原始失败与回归，普通产品路径实际接入；公共契约和持久化变化先形成可审阅接口 |
| CM-E4 冻结效果验证 | 建议每套 12 个独立留出任务、3 个预注册主对照、各 3 次；两套共 216 实例。根据开发实际用量在运行前冻结预算；另做独立 `live-full` 长任务，不能混入重放分母 | 完整失败、按任务块的不确定性、消耗与质量同时公开；不依据通过率挑组或重新评分。结果不支持收益时记录结论，不能因预算用完称成功 |
| CM-E5 公共外部参照（后续） | 优先 LongMemEval cleaned 的分层子集，保留原历史/时间/标签并记录数据 revision 和许可；预算允许再完整运行 | 子集、适配、原生官方完整运行分别命名；检索源命中与 QA 分开，不能拿子集结果进入完整榜单 |

E2 的 6 个任务是开发诊断样本，E4 的 24 个任务是两个 Suite 的统计单位；216 次执行不是 216 个独立任务。E4 的规模是方案建议，最终任务与预算在运行前固定，不能用观测到的分数决定补多少次。

### 9.1 推进与发表判断

- 保护门禁：独立任务中出现越界、无依据确认或重复副作用时必须修复，不能用平均分抵消。
- 效果判断：报告原版本、强基线与候选版本的配对完成差异和净消耗；证据区间较宽时只写该固定任务集的观测结果，不宣称普遍提升。
- 真实长任务门禁：要把 P2 压缩效果标记完成，仍需 `live-full` 的真实 20+ Turn 对照。完成重放 Suite 只能标记相应子项。
- 简历数字只来自版本固定的已运行结果，例如指定任务集的完成率、净输入/总 Token、冗余读取减少；不得将建议样本数、阈值或竞品成绩写为成果。
- 模型层更好的回答、程序门禁正确阻断、最终业务恢复是三类不同结果，分别归因。

## 10. 实施落点与回滚

- 评测编排与评分放在 `clawkit-evaluation`，数据定义放在 `benchmarks/`；实际交换留在显式输出目录，公共证据按现有脱敏与归档合同发布。
- 压缩与保护放在 `clawkit-context`；检查点的工作区持久化与会话生命周期归 `clawkit-engine`；通用记忆检索/存储归现有 memory 边界。Ops 的现场事实不反向写入通用 Context 业务逻辑。
- 新运行配置 opt-in；回滚至当前压缩/召回配置不删除用户记忆或旧证据。涉及版本迁移先保留原 Markdown，禁止评测清理真实 HOME。
- 先以任务失败定位缺口，再决定是否需要更复杂检索；P2-7 的版本/冲突设计按已有文档复用，不另造第二套记忆服务。
