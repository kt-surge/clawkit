# v1 失败分析与证据边界

## 协议问题

为了减少重复采证，开发时加入了“同一响应提交 submit_diagnosis 与 submit_decision”的提示。Runtime 已有明确合同：终止工具必须是批次唯一调用，混合批次完全不执行。该提示与合同冲突，真实运行出现拒绝、重试和预算耗尽。受控模型测试预设分轮调用，未能暴露提示问题；实际协议复验暴露了它。

CLAWKIT 全部十项为 MODEL_OR_PROTOCOL_FAILURE，不能据此断言知识本身无效或模型不会诊断。其他组也有预算、供应商失败和正确诊断但保守交接的样本。每项原始结果、实际用量和部分诊断均保留；系统最终 ESCALATE 不计模型成功。

修复保留 Runtime 门禁，要求诊断接受后另轮独占提交决定；新 v2 改变协议指导，场景、四组、种子、模型与预算维持相同。一次单项 OOM 协议开发复验通过，另一次供应商调用失败的 usage 不可得，两次分别保存。该开发通过不替代正式对照。

## 结论限制

- 强规则获得相同来源和反证，在此有限、可规则化的范围综合通过 10/10；没有 Agent 优于规则的证据。
- 缺失/过期/截断/冲突的四项合理未知单列，不把未知判断记为根因命中。
- 知识 REVIEWED 由合成正反例回放和受控审阅夹具提供，不是实际团队人工审阅。
- 事件关联是六对固定拓扑/时间窗受控合同，不是实际 Alertmanager 部署或共同根因推断评测。
- 每场景每组一次，没有模型稳定性、生产 MTTR、用户效率或商业化收益数据。
- 运行期间另一个工作树曾构建协议修复；耗时不是独占机器的性能基准。当前目录的源码输入及哈希独立冻结，原始证据审计通过。
